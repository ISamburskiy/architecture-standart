|1|Клиент + сайт|Просмотр ставок на депозиты|1. Неавторизованный клиент заходит на сайт<br>2. Неавторизованный клиент просматривает ставки по депозитам.|
|2|Клиент + сайт<br>Оператор КЦ + ПО КЦ|Заявка на депозит через сайт|1. Клиент создает заявку на депозит с указанием ФИО и номера телефона.<br>2. Заявка из бэкенда Сайта автоматически поступает в ПО кол-центра.<br>3. Оператор кол-центра просматривает заявку в ПО кол-центра.|
|3|Клиент + И-Б|Просмотр доступных депозитов в Интернет-Банке|1. Клиент заходит в Интернет-Банк.<br>2. Клиент просматривает доступные ему депозиты с учетом персональных условий.|
|4|Клиент + И-Б<br>Бэк-офис депозитов + АБС|Заявка на депозит через И-Б|1. Клиент создает заявку на депозит с указанием суммы депозита и счета списания средств<br>2. Если заявка подтверждена, сотрудник бэк-офиса создает депозит.<br>6. Клиенту приходит СМС о создании депозита.|
|5|Бэк-офис кредитов + АБС|Размещение информации о ставках|1. Сотрудник бэк-офиса кредитов заходит в АБС.<br>2. Сотрудник бэк-офиса кредитов размещает информацию о ставках|
|6|Бэк-офис депозитов + АБС|Просмотр информации о ставках|1. Сотрудник бэк-офиса депозитов заходит в АБС.<br>2. Сотрудник бэк-офиса депозитов просматривает информацию о ставках.|
### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
|1|Все сервисы должны быть доступны 99,9% времени 24 / 7.|
|2|В пользовательском интерфейсе время отклика на пользовательские действия должно быть порядка миллисекунд.|
|3|Данные из заявкок с Сайта и Интернет-Банка должны передаваться в зашифрованном виде.|
|4|Новую функциональность в рамках Интернет-Банка и Сайта реализуем отдельными микросервисами в рамках кластера Kubernetes (по возможности в кластер отдельным контейнером делаем текущие монолиты).|
|5|Вместе с новыми микросервисами реализуем BFF для маршрутизации запросов к монолитам и к новым микросервисам; а также для кэширования.|
|6|Вертикально масштабировать АБС.|
|7|Повысить производительность интеграции Интернет-Банка и Сайта с АБС.|

### <a name="_qmphm5d6rvi3"></a>**Решение**

<img width="1398" height="1034" alt="image" src="https://github.com/user-attachments/assets/8ef77880-6176-484f-bedd-dc3aebf6f067" />

В рамках Сайта и Интернет-Банка новая функциональность реализована микросервисами для удобства независимой разработки и развертывания. В рамках АБС в отдельный сервис выделен только изолированная функциональность по взаимодействию с Интернет-Банком и Сайтом, которая в дальнейшем использует общую логику Pl-Sql. Это сделано для создания посредника при обращении к БД для повышения надежности. Новое СМС-информирование будет реализовано имеющимися средствами СМС-информирования в АБС. Функциональность по заполнению и получению информации о ставке также реализована в текущей парадигме АБС.


### <a name="_bjrr7veeh80c"></a>**Альтернативы**
1. Дорабатывать текущие монолиты Сайта и Интернет-Банка. Не выбрано, т.к. повышает зависимость от платформы подрядчика + повышает взаимозависимость и затрудняет параллельную разработку.
2. Асинхронное взаимодействие между приложениями. Не выбрано из-за высоких удельных затрат на внедрение в рамках MVP, с учетом отсутствия опыта команды и проблем интеграции. Преимущества асинхронности частично реализованы с помощью сервисов-посредников.

**Недостатки, ограничения, риски**

Решение потребует несколько больше затрат на развертывание микросервисов.

Решение требует вертикального масштабирования БД АБС.

Решение потребует обучения сотрудников бэк-офиса процессу учета ставок.
